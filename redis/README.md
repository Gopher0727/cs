> Q：缓存和数据库怎么保持一致？
>
> A: 最常见的 Cache Aside。读时，查缓存，有就返回，没有就查数据库，然后**写回**缓存；写时，先更新数据库，再**删**缓存，一定要删，而不是改，因为并发改可能写入旧值。更严谨的做法，把“删缓存”放到消息队列重试，或者用 binlog 异步补偿，保障最终一致性。追求强一致，需要分布式事务，成本会很高。

> 分布式锁：NX EX
>
> 1. 先 SET 再 EXPIRE，如果两条命令中间宕机就死锁。
>
> 2. 直接 DEL 解锁，可能会删掉别人的锁。value 要存自己的身份标识。
>
> 3. 业务比过期时间长，导致锁提前释放，因此需要自动续期。

Redis 的消息队列：
- List：LPUSH、BRPOP，BRPOP 是阻塞，这样不需要轮询。但是，没有任何重试机制。
- Pub/Sub：广播在线，适合通知类场景。但是，消息不落地，断线期间收不到消息，没人订阅就丢弃。
- Stream：每条消息有自增 ID，支持重放和重试，同时支持消费者组。

> 分布式锁：关注多实例是否竞争同一个共享资源，以及锁过期问题。
>
> 哨兵：关注 Master 故障切换期间的请求失败、数据丢失、重连和幂等。
>
> Cluster：关注 Key 的分片规则，尤其是 Lua 脚本操作的多个 Key 是否位于同一个 Slot。
